# 實驗規格凍結與評估協定
## SO-ARM + LeRobot ｜國科會大專生研究計畫

**v1（8/11）｜收資料前必須全部填完並凍結**

> **來源：** 團隊討論、NVIDIA×NAPAI Sim2Real SO-101 工作坊講義（`260806_中央Sim2Real上課筆記.md`）
> **用途：** 這份是收資料期間反覆查閱的操作規範，不是一次性文件。

---

## 0. 為什麼要在收資料前凍結

**迭代預算：從 9 月到 12 月底約 16 週。一輪「收資料 → 訓練 → 評估」樂觀 3–5 天、含硬體問題 1–2 週。**

> ### 🔴 總共只有 8–16 次迭代機會。

規格沒凍結的後果不是「不夠嚴謹」，是**資料不能合併、實驗不能比較、一輪就報廢**。以八到十六輪的預算，報廢兩輪就傷筋動骨。

**凍結不等於永不改。** 凍結的意思是：**改動要有版本、有日期、有紀錄**，並明確標示「此後收集的資料屬於 v2」。否則「凍結」會變成兩個人心裡各自的版本。

## 1. 凍結清單 A｜任務與成功定義

**⚠️ 這是最基本也最常被跳過的一項。沒有這個，「成功率」是沒有意義的數字。**

| 項目 | 定義 | 填寫 |
|---|---|---|
| 任務描述（一句話） | | |
| **成功的判準** | 夾起來就算？要移到目標區？離桌面幾公分？要維持幾秒？ | |
| 部分成功是否計分 | 夾到但掉了＝失敗還是半分？ | |
| 單次 episode 的時間上限 | 超過即判失敗 | |
| 起始姿態 | 每次評估的手臂初始位置 | |

**失敗分類（收資料前就要定義，之後不准臨時新增類別）：**

| 代碼 | 類別 | 說明 |
|---|---|---|
| F1 | 沒抓到 | 夾爪閉合但物體不在其中 |
| F2 | 抓到後掉落 | 移動過程中脫手 |
| F3 | 撞擊 | 撞到物體／桌面／架子 |
| F4 | 沒動作 | 手臂未啟動或原地停滯 |

| F6 | 推走物體 | 接觸瞬間把輕物體推開（**空容器特有**） |
| F7 | 逾時 | 超過時間上限仍未完成 |

## 2. 凍結清單 B｜物體

**⚠️「垃圾夾取」太模糊。** 壓扁的寶特瓶與塑膠袋屬於**可變形物體**，透明物體對視覺**先天極難**——兩者都不該出現在 P0。

**凍結規則：5–8 個剛體、不透明、尺寸相近。**

| 級別 | 物體 | 階段 | 理由 |
|---|---|---|---|
| **L1 易** | 紙杯、紙團（緊實）、鋁罐（轉至貼紙面） | **P0** | 剛體、不透明、低反光 |
| L2 中 | 鋁罐（反光面）、不透明塑膠瓶 | P1 | 加入反光變因 |
| L3 難 | **透明寶特瓶**、皺褶塑膠袋 | P2 | 透明／可變形，經典難題 |

> 「**哪些材質特性使泛化夾取變難**」本身即為可量化的研究問題，比籠統宣稱「做泛化」清楚得多。

## 6. 評估指標分級

> 來源：工作坊講義（第 832–930 行）。**但不是全部都要用**——以下是對本計畫的取捨。

### P0 就要用（低成本、高價值）

| 指標 | 定義 | 為什麼現在就要 |
|---|---|---|
| **成功率** | 依第 1 節定義 | 基本盤 |
| **失敗類型分布** | 依 F1–F7 分類 | **這才是能指導下一步的東西**，成功率只告訴你好不好 |
| **干預率** | 每 100 次需人工救場幾次 | 講義稱為「黃金標準」。比成功率更反映可用性 |

### P1–P2 再加

| 指標 | 定義 | 何時用 |
|---|---|---|
| **OOD 壓力測試** | 極暗／極亮／逆光／雜亂背景下的性能衰減 | 進入泛化測試階段。**優秀模型應平緩下降而非斷崖式** |
| **顯著性映射** | 注意力熱圖——模型在看物體還是背景？ | 當成功率不明原因偏低時。**若模型靠背景顏色判斷，換背景就會抓空** |
| **節拍時間 vs 人類基準** | 完成一次動作的時間比 | 當模型變得過度小心緩慢時 |

### 本計畫先不用（成本高、與目標不符）

| 指標 | 為何暫緩 |
|---|---|
| 模型-硬體殘差 | 需要有數位孿生／模擬器對照。本計畫不走模擬路線 |
| 像素到力矩誤差 | 需要力矩量測，SO-101 無此感測 |
| 動作分塊對齊 | 有價值但需額外實作。**若出現漂移問題可提前啟用** |
| Jerk 分析 | 同上。若馬達異常發熱或磨損可啟用 |
| HIL 分析 | 需 Jetson 等邊緣裝置滿載測試，超出本計畫範圍 |

## 7. 環境與機器設定（實務陷阱）

### 預設工作流：用 LeRobot 官方工具

每次開工執行一次，約 30 秒：

```bash
lerobot-find-port        # 辨識哪個序列埠是哪支手臂（提示時拔掉其中一個裝置）
lerobot-find-cameras     # 列出相機並可預覽確認
```

**把結果當參數傳進去即可。這是 LeRobot 設計的工作流，對兩人單機的規模完全夠用。**

### 🔴 必做的一項

| 問題 | 對策 |
|---|---|
| **USB 頻寬不足會靜默掉 fps** | ⚠️ **不會報錯。錄完必須驗證實際 fps**（錄到的幀數 vs 時長 × 設定 fps），不符即重錄，並嘗試把其中一支相機換到**不同的 USB 控制器**（不只是同一個 hub 的別的孔） |

### 選配：udev / by-id 持久化綁定

> ⚠️ **先別做。** 這是「被咬過才升級」的路徑，不是初始設定。

`lerobot-find-port` 是**發現**工具（現在它在哪），udev 是**持久化**（永遠叫同一個名字）——兩者互補而非替代。但持久化的成本（需 sudo、要查 vendor/product/serial）只有在下列情況發生後才值得付：

- [ ] 相機 index 對調實際毀掉了一次錄製（wrist 影像存進了 front 欄位）
- [ ] 每天重跑 `find_port` 超過三次且明顯耗時
- [ ] 有 hardcode 裝置路徑的 config/script 反覆出錯
- [ ] 多人／多機共用同一組硬體且命名不一致

⚠️ **實驗室 GPU 機器不一定有 sudo**，沒有的話這條路本來就走不通，維持 find_port 即可。

升級步驟見 `scripts/setup_device_bindings.sh`。

> 講義明列：相機接反或編號跑掉是「機器人出現不可理喻舉動」的**最常見主因**。
> 在做綁定之前，**每次收資料與執行模型前用 `lerobot-find-cameras` 確認一次**就能防住這件事。

### 其他環境事項

- **Feetech SDK 需另外安裝**
- **使用者要加進 `dialout` group**（否則無權存取序列埠）
- **磁碟至少 200 GB**（多組對照實驗的 checkpoint 很吃空間）
- **訓練瓶頸可能在 dataloader（影片解碼）而非 GPU**
  → 若訓練慢，先看 **GPU 使用率、CPU 核心數、硬碟速度**，不要直接怪 GPU
- **選機器看獨佔性與可重灌性，不是看規格**
- **不要兩台電腦都裝環境**——維護成本翻倍

### 🔴 錄製機與評估機必須同一台、同一組相機設定

不同機器的 USB 控制器、相機驅動、時序都可能不同，會引入無法歸因的變因。

### ⚠️ 關於遠端推理（修正先前的建議）

工作坊用的是**雙終端機 client-server 架構**：一台跑策略伺服器、一台跑機器人客戶端。這看起來允許遠端推理，**但不要跨公網**。

> 講義：VLA 每秒僅輸出 10–30 次動作，指令不連續會表現為卡頓與抖動，
> 「會產生巨大的瞬間反向作用力，造成**嚴重磨損甚至破壞伺服馬達與減速齒輪**」。

**界線：**
- ✅ 遠端可做：開發、訓練、資料檢視、看攝影機畫面
- ❌ 遠端不可做：**跨公網跑推理控制實體手臂**
- 策略伺服器與機器人客戶端應在**同一台或同一區網**

## 8. 決策規則（在看到數字之前就先寫死）

> **這是防止盲目試錯的核心機制。** 迭代預算只有 8–16 輪，不能靠感覺決定下一步。

| 成功率 | 該做什麼 | **不該做什麼** |
|---|---|---|
| **< 30%** | 查**資料表達**：action representation、相機視角、校正漂移、schema 是否正確 | ❌ **不要換模型** |
| **30–60%** | **加資料、改收集品質**（含 recovery demo 比例） | ❌ **不要換 policy** |
| **> 60–70%** | 才進入第二階段：換 policy 做比較 | — |

### 停損與求助門檻（本團隊補充）

> **單一問題卡超過 4 小時 → 停下來，寫成三行（卡在哪／試過什麼／錯誤訊息），求助。**

不是示弱，是把回饋週期從「幾天」縮短到「一天」。以 8–16 輪的預算，卡三天就等於燒掉半輪。

## 9. 兩人團隊的特有風險

### 🔴 demo 操作者一致性

講義明確要求：「動作務必保持**平滑與直接**（不要繞路）……這對後續訓練 AI 模型非常關鍵。」

**若兩人都錄 demo，操作風格差異會直接變成資料裡的雜訊。**

**對策（三選一）：**
1. 一人錄全部（最乾淨）
2. 先對齊操作規範，**並在每條 demo 的 metadata 記錄操作者**，之後可分析是否有差異
3. 兩人各錄一批，先做一次 A/B 比較確認風格差異可忽略

### 分工介面（現場者 ↔ 遠端者）

**資料格式規範必須在對方進場「之前」給出。**

**現場者必須帶回來的東西：**
- [ ] 校正 JSON 檔
- [ ] port 名稱（`lerobot-find-port` 輸出）
- [ ] **相機實測解析度與 fps**（不是規格上的，是實測的）
- [ ] 電腦規格（CPU 核心數、RAM、GPU、硬碟類型）
- [ ] 現場照片（器材、場地、相機位置、走線）
- [ ] 器材型號與韌體版本

**第一趟只錄 3–5 條 demo，目的是驗證格式，不是收資料。**

## 10. Pilot：走完全鏈路，不只驗證格式

> 只驗證格式不夠。**要用最小資料量把整條鏈路跑通一次。**

```
錄 10 條 demo（含 2–3 條 recovery）
  ↓
訓練一次 ACT（過擬合也沒關係，重點是流程通）
  ↓
真機評估 5 次（不看成功率，只看流程能不能跑完）
  ↓
確認：資料格式 ✓ 訓練腳本 ✓ 評估腳本 ✓ 記錄表格 ✓
  ↓
才開始正式收 50 條
```

**理由：** 否則可能收滿 200 條，才發現評估腳本或 schema 有問題。以 8–16 輪的預算，這種錯誤付不起。

### 🔴 訓練驗證必須跑滿至少一個 epoch

「訓練一次」不等於「資料驗證過」。**短步數的 smoke test 只會碰到極小一部分資料。**

2026-08-12 在公開資料集上實測（僅用於驗流程，非本計畫用資料）：

| 跑法 | 涵蓋範圍 | 結果 |
|---|---|---|
| 100 步 @ batch 8 | `epch:0.01`，不到 1% 的資料 | ✅ 全綠：loss 下降、checkpoint 存出 |
| 1000 步 @ batch 32 | 跑到第 4 個 epoch 邊界 | ❌ 第 167 步崩潰 |

崩潰原因是該資料集**內部不一致**：`meta/info.json` 宣稱 61,480 幀，實際影片共 61,534 幀，差額全在 `file-000`（實際 7,767 幀 vs metadata 推得 7,713 幀）。全域索引因此錯位，越界時才拋 `IndexError: Invalid frame index=8530 ... must be less than 8524`。

**關鍵風險：這種損壞在錄製當下不會報錯，只在訓練讀到那一段時才炸。** 而且 `--dataset.exclude_episodes` 排除受影響的 episode **也救不了**（改成 sampler 的 `KeyError`，索引空間仍由錯誤的總幀數建立）。

因此 Pilot 的「訓練一次」一項，驗收標準改為：

- [ ] 訓練步數 × batch size **≥ 資料集總幀數**（即至少完整走過一遍）
- [ ] 錄製後立即比對 `meta/info.json` 的 `total_frames` 與影片實際幀數是否相符

## 11. 硬體現實（SO-101 的先天限制）

- **SO-101 使用航模等級伺服機，backlash（齒輪背隙）會沿運動學鏈累積**
  → **精密插入類任務先天不利**。本計畫是「夾取並移到目標區」，不是「插進狹孔」，尚可接受
  → 但要在報告中誠實說明此限制
- 講義的累積誤差說明：模擬與現實摩擦力差 2%，第一步偏 0.5 mm，經過抓取→提起→移動→對準，**最終可能擴大到數公分**
- **備品與交期**：舵機、夾爪等易損件，**台灣代理商可能要兩週**
  → **現在就下單常用備品**，不要等壞了才叫
