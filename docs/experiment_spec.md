## 0. 為什麼要在收資料前凍結

**迭代預算：從 9 月到 12 月底約 16 週。一輪「收資料 → 訓練 → 評估」樂觀 3–5 天、含硬體問題 1–2 週。**

> ### 🔴 總共只有 8–16 次迭代機會。

規格沒凍結的後果不是「不夠嚴謹」，是**資料不能合併、實驗不能比較、一輪就報廢**。以八到十六輪的預算，報廢兩輪就傷筋動骨。

**凍結不等於永不改。** 凍結的意思是：**改動要有版本、有日期、有紀錄**，並明確標示「此後收集的資料屬於 v2」。否則「凍結」會變成兩個人心裡各自的版本。

## 1. 凍結清單 A｜任務與成功定義

**⚠️ 這是最基本也最常被跳過的一項。沒有這個，「成功率」是沒有意義的數字。**

> **v2（2026-08-12）：** 已納入 8/11 會議的基礎假設，並改為**結果／機制兩軸**。
> **✅ v3（2026-08-13）：兩軸方案已於會議決議通過**，負責人陳霆翰。見 `docs/decisions.md` D015、
> `docs/meeting/2026-08-13.md` 三之決議表。

### 1-1 任務定義

| 項目 | 定義 |
|---|---|
| 任務描述 | 從固定起始姿態出發，夾取工作區內的單一空容器，移至固定目標區上方後鬆開夾爪，使物體落入車體上的固定垃圾桶 |
| **成功判準** | **夾起 → 移至目標區 → 鬆開 → 物體落入垃圾桶內** |
| 起始姿態 | **固定姿態，且該姿態下相機畫面中已可看見目標物** |
| 單次 episode 時間上限 | ⚠️ 暫定 20 秒——**須以下方方法驗證後定案** |

> ⚠️ **「起始姿態即可見目標」是一個範圍決定，要記錄下來：**
> 它把**搜尋階段**整個排除在任務之外。所以本計畫測的是「接近＋夾取＋放置」，
> 不是「找到＋接近＋夾取＋放置」。報告中必須明講，否則會被誤讀為完整的撿拾流程。

### 1-2 ⚠️ 時間上限 20 秒是否合理——不要用猜的

**先估算：** 順暢執行一次約為 接近 3–5s ＋ 夾取 2s ＋ 搬運 3–5s ＋ 鬆開 1s ≈ **10–13 秒**。
20 秒 ≈ 1.5–2 倍，看似合理。

**但有一個會咬人的交互作用：**

> 🔴 **timeout 設太短，會把「原本會成功修正回來」的 rollout 判成失敗。**
> 而「能不能從偏離狀態修正回來」正是 A3 要測的核心行為。
> **timeout 過短 = 系統性地壓低 recovery 行為的分數 = 讓 A3 測不到它想測的東西。**

**定案方法（有原則，不靠猜）：**

1. 錄 10 條人類遙操作 demo，量測每條的實際完成時間
2. 取中位數 × **2.5**（留出修正的餘裕），四捨五入到整秒
3. 若算出來仍接近 20 秒 → 20 秒定案；若明顯更長 → 採用算出的值

**在硬體到位前，20 秒作為暫定值可用於文件與規劃，但不得作為評估的最終依據。**

### 1-3 失敗與結果分類：兩軸

**問題：** 原本的 F1–F7 混了兩種分類軸。「推走物體」之後結果必然是「沒抓到」——標註者會猶豫填哪個，兩人會填不一樣，統計出來的分布沒有意義。

**方案：拆成兩欄，各自互斥。**

**① `outcome`（互斥、窮盡 — 用來算成功率）**

| 值 | 說明 |
|---|---|
| `success` | 物體落入垃圾桶內 |
| `no_grasp` | 沒抓起來 |
| `dropped` | 抓起來了但中途掉落 |
| `misplaced` | 移到了但沒落入目標區內 |

**② `mechanism`（可複選、可留空 — 用來決定下一輪改什麼）**

| 值 | 說明 |
|---|---|
| `pushed_away` | 接觸瞬間把輕物體推開（**空容器特有**） |
| `collision` | 撞到物體／桌面／垃圾桶 |
| `drift` | 單向偏移出工作區（工作坊已觀察到此模式） |
| `stalled` | 未啟動或原地停滯 |
| `repetition_loop` | 死循環重複動作（局部震盪/原地重複軌跡） |
| `timeout` | 到達時間上限 |
| **`self_recovered`** | ⭐ **偏離後自行修正並完成**（`outcome` 為 `success` 時也可標） |
| `other` | 需在 notes 詳述 |

> ⭐ **`self_recovered` 是刻意放進來的正向標籤。**
> `mechanism` 欄記錄的是「值得注意的行為」，不只是失敗原因。
> 若 recovery demo 有效，實機評估時這個標籤的出現次數應該上升——
> **那是 A3 假設在真實硬體上最直接的證據。**
> （人工介入救回不需另設標籤，`intervention` 欄已涵蓋。）

**③ `valid`（無效試驗剔除）**

| 欄位 | 值 |
|---|---|
| `valid` | `1` = 有效／`0` = 無效，不計入成功率分母 |
| `void_reason` | 馬達過熱、相機掉線、人為誤觸、其他 |

> 沒有這一欄，硬體問題會污染成功率。**一次因為相機掉線而失敗的 trial，不該算模型的帳。**

**規則：`outcome` 一定要填一個值；`mechanism` 可以 0 到多個；新增任何代碼＝規格變更，須升版並記錄於 §12。**

## 2. 凍結清單 B｜物體

**⚠️「垃圾夾取」太模糊。** 壓扁的寶特瓶與塑膠袋屬於**可變形物體**，透明物體對視覺**先天極難**——兩者都不該出現在 P0。

**凍結規則：5–8 個剛體、不透明、尺寸相近。**

**已整合 2026-08-11 會議決議的三項物體（鋁罐、不透明寶特瓶、紙杯），並依難度分級：**

| 級別 | 物體 | 階段 | 理由 |
|---|---|---|---|
| **L1 易** | **紙杯** ★會議決議<br>**鋁罐（轉至貼紙面）** ★會議決議<br>紙團（緊實） | **P0** | 剛體、不透明、低反光 |
| L2 中 | **不透明寶特瓶** ★會議決議<br>鋁罐（反光面） | P1 | 加入反光變因；瓶身較高、抓取點選擇較多 |
| L3 難 | **透明寶特瓶**、皺褶塑膠袋 | P2 | 透明／可變形，視覺抓取的經典難題 |

> ⚠️ **同一個鋁罐依朝向被分到兩級**——貼紙面朝上是 L1，裸鋁面朝上是 L2。
> 這不是分類混亂，是刻意的：**它讓「反光」成為單一受控變因**，其餘條件完全相同。
> 收資料與評估時必須記錄朝向。

> 「**哪些材質特性使泛化夾取變難**」本身即為可量化的研究問題，比籠統宣稱「做泛化」清楚得多。

> 這不代表過渡計畫是錯的，代表它是一個**有假說的實驗條件**，不是理所當然沒事的權宜之計。

## 5-B. 🔴 校正協定

> **選 SO-ARM 就等於接手了校正責任**（OMX 出廠已校準，SO-ARM 沒有）。
> 這是本團隊已知的兩次失敗來源——工作坊的校正檢查、專題缺乏系統性校正流程——
> 因此不能當成「開始前做一次的雜事」。

### 每次資料收集前

- [ ] 執行官方校正檢查腳本
- [ ] **要求 `Overall: ✓ PASS`。不 PASS 不收資料**
- [ ] 校正檔存入 `calibration/`，檔名帶日期（例：`2026-08-20_follower.json`）
- [ ] 拍攝場地基準照：相機位置、桌面配置、光源
- [ ] 驗證相機索引（`lerobot-find-cameras`）

### 每次評估前

- [ ] 重複上述檢查
- [ ] **記錄本次評估使用哪一份校正檔**（填入 `eval/` 的 run metadata）

### 每個 dataset

- [ ] README 註明：對應校正檔檔名、場地基準照、收集日期、操作者

> ★ **核心原則：資料與校正狀態必須綁定。**
> 當某批資料訓出的模型效果特別差時，才能回頭查證「是不是那天校正跑掉了」。
> 工作坊那次無法回頭驗證，正是因為沒有留下當時的數據與校正狀態。

### 校正的已知地雷（取自工作坊講義）

| 地雷 | 後果 |
|---|---|
| **全範圍掃描沒推到真正的機械死點** | 手臂撞到線材或異物就停止 → 記錄到錯誤極限值 → **整台機器人校準失效** |
| 線材被夾在關節連桿之間 | 同上 |
| 手腕軸初始未精準居中 | 編碼器溢位 |
| **相機索引跳號** | 講義列為「機器人出現不可理喻舉動」的**最常見主因** |

## 6. 評估指標分級

> 來源：工作坊講義（第 832–930 行）。**但不是全部都要用**——以下是對本計畫的取捨。

### P0 就要用（低成本、高價值）

| 指標 | 定義 | 為什麼現在就要 |
|---|---|---|
| **成功率** | 依第 1 節定義 | 基本盤 |
| **失敗類型分布** | 依 F1–F7 分類 | **這才是能指導下一步的東西**，成功率只告訴你好不好 |
| **干預率** | 每 100 次需人工救場幾次 | 講義稱為「黃金標準」。比成功率更反映可用性 |

### P1–P2 再加

| 指標 | 定義 | 何時用 |
|---|---|---|
| **OOD 壓力測試** | 極暗／極亮／逆光／雜亂背景下的性能衰減 | 進入泛化測試階段。**優秀模型應平緩下降而非斷崖式** |
| **顯著性映射** | 注意力熱圖——模型在看物體還是背景？ | 當成功率不明原因偏低時。**若模型靠背景顏色判斷，換背景就會抓空** |
| **節拍時間 vs 人類基準** | 完成一次動作的時間比 | 當模型變得過度小心緩慢時 |

### 本計畫先不用（成本高、與目標不符）

| 指標 | 為何暫緩 |
|---|---|
| 模型-硬體殘差 | 需要有數位孿生／模擬器對照。本計畫不走模擬路線 |
| 像素到力矩誤差 | 需要力矩量測，SO-101 無此感測 |
| 動作分塊對齊 | 有價值但需額外實作。**若出現漂移問題可提前啟用** |
| Jerk 分析 | 同上。若馬達異常發熱或磨損可啟用 |
| HIL 分析 | 需 Jetson 等邊緣裝置滿載測試，超出本計畫範圍 |

## 7. 環境與機器設定（實務陷阱）

### 預設工作流：用 LeRobot 官方工具

每次開工執行一次，約 30 秒：

```bash
lerobot-find-port        # 辨識哪個序列埠是哪支手臂（提示時拔掉其中一個裝置）
lerobot-find-cameras     # 列出相機並可預覽確認
```

**把結果當參數傳進去即可。這是 LeRobot 設計的工作流，對兩人單機的規模完全夠用。**

### 🔴 必做的一項

| 問題 | 對策 |
|---|---|
| **USB 頻寬不足會靜默掉 fps** | ⚠️ **不會報錯。錄完必須驗證實際 fps**（錄到的幀數 vs 時長 × 設定 fps），不符即重錄，並嘗試把其中一支相機換到**不同的 USB 控制器**（不只是同一個 hub 的別的孔） |

### 選配：udev / by-id 持久化綁定

> ⚠️ **先別做。** 這是「被咬過才升級」的路徑，不是初始設定。

`lerobot-find-port` 是**發現**工具（現在它在哪），udev 是**持久化**（永遠叫同一個名字）——兩者互補而非替代。但持久化的成本（需 sudo、要查 vendor/product/serial）只有在下列情況發生後才值得付：

- [ ] 相機 index 對調實際毀掉了一次錄製（wrist 影像存進了 front 欄位）
- [ ] 每天重跑 `find_port` 超過三次且明顯耗時
- [ ] 有 hardcode 裝置路徑的 config/script 反覆出錯
- [ ] 多人／多機共用同一組硬體且命名不一致

⚠️ **實驗室 GPU 機器不一定有 sudo**，沒有的話這條路本來就走不通，維持 find_port 即可。

升級步驟見 `scripts/setup_device_bindings.sh`。

> 講義明列：相機接反或編號跑掉是「機器人出現不可理喻舉動」的**最常見主因**。
> 在做綁定之前，**每次收資料與執行模型前用 `lerobot-find-cameras` 確認一次**就能防住這件事。

### 其他環境事項

- **Feetech SDK 需另外安裝**
- **使用者要加進 `dialout` group**（否則無權存取序列埠）
- **磁碟至少 200 GB**（多組對照實驗的 checkpoint 很吃空間）
- **訓練瓶頸可能在 dataloader（影片解碼）而非 GPU**
  → 若訓練慢，先看 **GPU 使用率、CPU 核心數、硬碟速度**，不要直接怪 GPU
- **選機器看獨佔性與可重灌性，不是看規格**
- **不要兩台電腦都裝環境**——維護成本翻倍

### 🔴 錄製機與評估機必須同一台、同一組相機設定

不同機器的 USB 控制器、相機驅動、時序都可能不同，會引入無法歸因的變因。

### ⚠️ 關於遠端推理（修正先前的建議）

工作坊用的是**雙終端機 client-server 架構**：一台跑策略伺服器、一台跑機器人客戶端。這看起來允許遠端推理，**但不要跨公網**。

> 講義：VLA 每秒僅輸出 10–30 次動作，指令不連續會表現為卡頓與抖動，
> 「會產生巨大的瞬間反向作用力，造成**嚴重磨損甚至破壞伺服馬達與減速齒輪**」。

**界線：**
- ✅ 遠端可做：開發、訓練、資料檢視、看攝影機畫面
- ❌ 遠端不可做：**跨公網跑推理控制實體手臂**
- 策略伺服器與機器人客戶端應在**同一台或同一區網**

## 9. 兩人團隊的特有風險

### 🔴 demo 操作者一致性

講義明確要求：「動作務必保持**平滑與直接**（不要繞路）……這對後續訓練 AI 模型非常關鍵。」

**若兩人都錄 demo，操作風格差異會直接變成資料裡的雜訊。**

**對策（三選一）：**
1. 一人錄全部（最乾淨）
2. 先對齊操作規範，**並在每條 demo 的 metadata 記錄操作者**，之後可分析是否有差異
3. 兩人各錄一批，先做一次 A/B 比較確認風格差異可忽略

### 分工介面（現場者 ↔ 遠端者）

**資料格式規範必須在對方進場「之前」給出。**

**現場者必須帶回來的東西：**
- [ ] 校正 JSON 檔
- [ ] port 名稱（`lerobot-find-port` 輸出）
- [ ] **相機實測解析度與 fps**（不是規格上的，是實測的）
- [ ] 電腦規格（CPU 核心數、RAM、GPU、硬碟類型）
- [ ] 現場照片（器材、場地、相機位置、走線）
- [ ] 器材型號與韌體版本

**第一趟只錄 3–5 條 demo，目的是驗證格式，不是收資料。**

## 10. Pilot：走完全鏈路，不只驗證格式

> 只驗證格式不夠。**要用最小資料量把整條鏈路跑通一次。**

```
錄 10 條 demo（含 2–3 條 recovery）
  ↓
訓練一次 ACT（過擬合也沒關係，重點是流程通）
  ↓
真機評估 5 次（不看成功率，只看流程能不能跑完）
  ↓
確認：資料格式 ✓ 訓練腳本 ✓ 評估腳本 ✓ 記錄表格 ✓
  ↓
才開始正式收 50 條
```

**理由：** 否則可能收滿 200 條，才發現評估腳本或 schema 有問題。以 8–16 輪的預算，這種錯誤付不起。

### 🔴 訓練驗證必須跑滿至少一個 epoch

「訓練一次」不等於「資料驗證過」。**短步數的 smoke test 只會碰到極小一部分資料。**

2026-08-12 實測。用的是公開資料集 `edgarcancinoe/soarm101_pickplace_orange_080e_ts_closed`
（**僅用於驗流程，非本計畫用資料**）—— 特意寫出名稱，下面的數字才查得證：

| 跑法 | 涵蓋範圍 | 結果 |
|---|---|---|
| 100 步 @ batch 8 | `epch:0.01`，不到 1% 的資料 | ✅ 全綠：loss 下降、checkpoint 存出 |
| 1000 步 @ batch 32 | 跑到第 4 個 epoch 邊界 | ❌ 第 167 步崩潰 |

崩潰原因是該資料集**內部不一致**：`meta/info.json` 宣稱 61,480 幀，實際影片共 61,534 幀，差額全在 `file-000`（實際 7,767 幀 vs metadata 推得 7,713 幀）。全域索引因此錯位，越界時才拋 `IndexError: Invalid frame index=8530 ... must be less than 8524`。

**關鍵風險：這種損壞在錄製當下不會報錯，只在訓練讀到那一段時才炸。** 而且 `--dataset.exclude_episodes` 排除受影響的 episode **也救不了**（改成 sampler 的 `KeyError`，索引空間仍由錯誤的總幀數建立）。

因此 Pilot 的「訓練一次」一項，驗收標準改為：

- [ ] 訓練步數 × batch size **≥ 資料集總幀數**（即至少完整走過一遍）
- [ ] 錄製後立即比對 `meta/info.json` 的 `total_frames` 與影片實際幀數是否相符
