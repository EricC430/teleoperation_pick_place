## 二、本次議程（需兩人共識）

### 1. 🔴 失敗分類要不要改成兩軸？

**問題：** 8/11 決議的失敗分類（沒抓到／抓到掉了／撞到出界／沒放到指定區域），以及後續擴充的 F1–F7，**混了兩種分類軸**：

| 代碼 | 描述的是 |
|---|---|
| F1 沒抓到、F2 抓到後掉落、F7 逾時 | **結果** |
| F3 撞擊、F4 沒動作、F5 漂移出界、F6 推走物體 | **機制** |

**重疊的具體例子：**
- 「推走物體」（F6）之後，結果必然是「沒抓到」（F1）→ 標註者會猶豫填哪個，兩人會填不一樣
- 「原地停滯」（F4）持續下去必然「逾時」（F7）
- 「撞擊」（F3）可能導致 F1、F2 或 F7

**後果：** 標註不一致 → 失敗類型分布的統計沒有意義 → 而**失敗分布正是唯一能指導「下一輪該改什麼」的指標**。

**提案：拆成兩欄，各自互斥**

| 欄位 | 值 | 性質 |
|---|---|---|
| `outcome` | `success` / `no_grasp` / `dropped` / `misplaced` | **互斥、窮盡**。用來算成功率 |
| `mechanism` | `pushed_away` / `collision` / `drift` / `stalled` / `timeout` / **`self_recovered`** / `other` | 可複選、可留空。用來決定改什麼 |
| `valid` | `0` / `1` ＋ `void_reason` | **無效試驗剔除**（馬達過熱、相機掉線、人為誤觸），不計入成功率分母 |

**⭐ 注意 `mechanism` 裡的 `self_recovered`：** 這個標籤記錄「模型偏掉了但自己修正回來並成功」。
`outcome` 是 `success`，但這個行為值得單獨追蹤——**因為它正是 A3 假設要驗證的能力。**
若 recovery demo 有效，實機評估時 `self_recovered` 的出現次數應該上升，那是最直接的證據。

（人工介入救回的情況不用另設標籤——已有 `intervention` 欄。）

**待決：** 同意改嗎？同意的話 `experiment_spec.md` §1 與 `eval/` 模板一併更新。

### 2. 🔴 測試集數量與統計效力

A3 實驗的樣本量規劃（詳見 `exp_a3_recovery_ablation.md` §7）：

| 項目 | 建議下限 | 理由 |
|---|---|---|
| 每組訓練 episode | **30–50** | ACT 的實務下限 |
| **留出測試 episode** | **≥ 20** | 低於此，成功率的信賴區間過寬 |
| **每組 random seed 數** | **≥ 3** | 🔴 **不可省** |

**seed 這條要特別討論：**
> 如果組間差異小於組內 seed 變異，我們報告的就是雜訊。
> 3 個 seed × 2 組 = **6 次訓練**。這會直接吃掉訓練預算，所以要先確認 GPU 時間與 checkpoint 空間夠不夠。

**另一個必須控制的變因：** 兩組的**訓練 episode 數量必須相同**。
若組 B 只是資料比較多，實驗測到的是「資料量」不是「資料組成」。
→ 作法：固定總數，只改變「含修正軌跡的比例」。

**待決：**
- 測試集抓 20 還是更多？
- 6 次訓練的 GPU 時間與磁碟空間估算（柏宇本週跑過一輪後應該有數字）

### 5. ⚠️ Windows 筆電當錄製機是否可行

**未驗證的前提：** LeRobot 主要在 Linux 開發與測試。筆電是 Windows。

**需要今明兩天查證：**
- LeRobot 官方文件有無 Windows 支援說明？
- 社群有無人在 Windows 上跑通 SO-ARM 的 teleoperation 與錄製？
- Feetech SDK 的序列埠存取在 Windows 上是否正常？

**⚠️ 不要用 WSL2 做錄製。** USB 相機在 WSL2 的直通支援很差，這是常見的坑。

**若 Windows 不可行，備案：** 改用實驗室某台 Linux 機器同時當錄製機與評估機。

**🔴 硬性限制（無論用哪台）：錄製機與評估機必須是同一台。**
USB 控制器、相機驅動、時序都會影響資料；換機器等於引入無法歸因的變因。
訓練可以在別台（純計算，不碰硬體）。
